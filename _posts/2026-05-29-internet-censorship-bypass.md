2026년 들어 한국의 인터넷 차단 방식이 SNI 필터링에서 Cloudflare 직접 압박으로 옮겨가면서, 차단 기술과 우회 기술이 어떻게 맞물려 발전해 왔는지 네트워크 보안 관점에서 정리한다. 외부 침해 사고는 아니지만, 네트워크 통제 방식이 바뀌면서 이용자 프라이버시와 서비스 접근성에 영향을 준 최신 보안 이슈로 볼 수 있다.

## 01 사건 개요

한국의 인터넷 차단은 오랫동안 **SNI 필드 차단** 방식에 의존해 왔다. 그런데 사용자들이 SNI를 암호화하는 기술(ESNI/ECH)로 이를 우회하기 시작했고, 정부는 이에 대응해 **차단을 우회하게 해주던 Cloudflare 측을 직접 압박**하는 방향으로 전략을 바꿨다.[1]

2026년 5월부터는 해외 사이트 접속 시 방송통신심의위원회의 기존 차단 화면(warning.or.kr) 대신 **Cloudflare의 HTTP 451 차단 안내**가 뜨기 시작했다.[2] 차단 방식의 근본적인 변화를 보여주는 장면이다.

> **이 글의 관점**
>
> 이 주제는 표현의 자유·통신비밀 같은 정책적 쟁점을 포함하지만, 이 글은 **네트워크 보안 기술 관점**에서 차단과 우회가 기술적으로 어떻게 작동했고, 왜 기존 대응이 한계에 부딪혔는지를 중심으로 정리한다.

## 02 배경 — HTTPS와 SNI의 구조

왜 차단의 핵심이 SNI였는지 이해하려면 HTTPS 연결 과정을 봐야 한다. 브라우저가 HTTPS 사이트에 접속할 때는 TLS 핸드셰이크를 거친다. 이때 클라이언트가 "내가 접속하려는 도메인은 이것"이라고 알려주는 필드가 **SNI(Server Name Indication)**다.[3]

> **SNI (Server Name Indication)** — 하나의 서버 IP가 여러 도메인을 호스팅하는 경우(reverse proxy, CDN 등), 클라이언트가 어떤 도메인의 인증서를 원하는지 서버에 알려주기 위한 TLS 확장 필드. 문제는 이 필드가 **암호화되지 않은 채(평문)** 전송된다는 점이다.

```text
클라이언트 → 서버 : TLS ClientHello
   └ SNI: example.com  (평문, 누구나 볼 수 있음)
   ↓
서버 → 클라이언트 : 해당 도메인 인증서 전달
   ↓
암호키 교환 → 이후 통신은 암호화
```

본문 통신은 암호화되지만, 핸드셰이크 단계의 SNI는 평문이다. 그래서 통신사 중간에 놓인 차단 장비가 이 SNI를 들여다보고 "차단 대상 도메인이면 연결을 끊는" 방식이 가능했다.[3]

## 03 차단 기술의 변화 과정

### 3-1. URL/DNS 차단 (초기)

초기에는 HTTP 평문 통신의 URL을 보거나, DNS 응답을 조작해 차단 페이지(warning.or.kr)로 보내는 방식이 쓰였다. 하지만 HTTPS가 보편화되고 사용자가 DNS 서버를 바꾸면 쉽게 우회됐다.

### 3-2. SNI 필드 차단 (2019~)

2019년 2월, SNI 차단 기술이 도입됐다.[4] 2024년에는 방송통신심의위원회가 KT, SK브로드밴드, LG유플러스 등 통신사에 SNI 필드 차단 기술로 접근을 제한하도록 시정 요구했다.[3] HTTPS 환경에서도 평문으로 남아 있는 SNI를 이용한 것이다.

> **SNI 차단의 논란점**
>
> SNI 차단은 차단 장비가 사용자의 HTTPS 통신 과정을 들여다보는 데서 시작된다. 이 때문에 통신비밀·감청 논란이 제기됐다. 기술적으로도, 사용자가 핸드셰이크 자체를 가리면 무력화된다는 한계가 있었다.

## 04 우회 기술의 변화 과정

SNI가 평문이라는 점이 차단의 근거였으므로, 우회 기술은 자연스럽게 **SNI를 가리는 방향**으로 발전했다.

### 4-1. ESNI (Encrypted SNI)

SNI 필드 자체를 암호화하는 기술이다. 차단 장비가 도메인 정보를 읽을 수 없게 만든다. Cloudflare가 이를 지원하면서 많은 사이트가 다시 검열을 우회할 수 있게 됐다.[5]

### 4-2. ECH (Encrypted Client Hello)

ESNI의 후속 기술로, SNI뿐 아니라 ClientHello 전체를 암호화한다. ECH가 대중화되면 중간 장비가 핸드셰이크에서 도메인 정보를 얻을 방법이 사실상 사라진다.[6]

> **ECH (Encrypted Client Hello)** — TLS 핸드셰이크의 첫 메시지인 ClientHello를 통째로 암호화하는 표준. SNI를 포함한 메타데이터가 평문 노출되지 않으므로, SNI 기반 차단을 근본적으로 무력화한다.

> **차단 측의 딜레마**
>
> ECH/ESNI 기반 접속을 막으려면 "암호화된 핸드셰이크 자체를 전부 차단"하는 수밖에 없는데, 이렇게 하면 정상 사이트 상당수도 함께 망가진다. 그래서 SNI 차단만으로는 ECH 시대에 대응하기 어렵다는 분석이 나왔다.[6] 중국은 이 문제 때문에 ESNF에 대한 사용 자체를 차단하는 방식을 택했다.

## 05 탐지와 대응 타임라인

핸드셰이크를 들여다보는 방식이 한계에 부딪히자, 차단 전략은 **우회를 가능하게 해주던 사업자를 직접 압박**하는 쪽으로 바뀌었다. 우회의 핵심 인프라가 된 Cloudflare가 그 대상이었다.[5]

- **2019-02** — SNI 필드 차단 기술 도입
- **2024** — 방심위, 통신 3사에 SNI 차단 시정 요구
- **2025** — 정부가 Cloudflare에 접속 차단을 요구한 사실이 드러남
- **2026-05-01** — 해외 성인·게임 사이트 접속 시 방심위 차단 화면 대신 **Cloudflare 접근 제한 공지** 등장
- **2026-05-11** — **긴급차단제 시행** — 사전 심의 없이 차단 가능

그 결과 한국에서 차단 대상 사이트에 접속하면 Cloudflare가 반환하는 **HTTP 451 ("법적 사유로 이용 불가")** 응답이 표시된다.[6] 차단 주체가 통신사 중간 장비에서 CDN 사업자 쪽으로 이동한 것이다.

> **HTTP 451** — "Unavailable For Legal Reasons". 법적 요구로 콘텐츠 접근이 제한될 때 반환하는 상태 코드다. 차단이 네트워크 중간 조작이 아니라 서비스 제공자 단에서 명시적으로 이뤄지고 있음을 보여준다.

> **2026년 추가 쟁점 — AI 사전 검열**
>
> 같은 시기 전기통신사업법 시행령 개정으로, 불법촬영물 유통 방지를 위한 기술적 조치 대상이 동영상에서 이미지까지 확대됐다(2026년 7월 시행 예정). 커뮤니티들은 업로드되는 이미지를 AI로 사전 필터링해야 해서 서버 부담과 서비스 품질 저하가 우려된다고 밝혔다.[1] 차단(접근 제한)과 사전 검열(업로드 필터링)이라는 두 축이 동시에 강화되는 흐름이다.

## 06 근본 원인

### 원인 1 — 평문 메타데이터에 의존한 차단 구조

이 전체 공방의 출발점은 "SNI가 평문이었다"는 기술적 사실이다. 통신 본문을 암호화해도 메타데이터(접속 도메인, 시점, 크기 등)가 평문으로 남으면 분석·차단의 근거가 된다. 보안 설계에서 메타데이터 보호가 본문 암호화만큼 중요하다는 점을 보여준다.

### 원인 2 — 차단과 우회가 계층을 옮겨가며 반복되는 구조

URL → DNS → SNI → ECH로 올라가는 동안, 차단과 우회는 각자 한 계층 위로 이동하며 대응해 왔다. 결국 핸드셰이크를 다 가리자, 차단은 네트워크 계층을 떠나 CDN 사업자라는 응용/운영 계층으로 옮겨갔다. 한 지점을 막으면 다른 지점으로 이동하는 구조다.

### 원인 3 — 중앙 인프라 의존의 양면성

Cloudflare 같은 소수의 CDN에 트래픽이 집중되면서, 이들이 우회의 핵심이자 동시에 차단의 지렛대가 됐다. 인프라가 집중될수록 한 사업자에 대한 압박만으로 광범위한 통제가 가능해진다는 점은 보안·가용성 관점에서도 생각해 볼 지점이다.

## 07 대응 방법과 미흡했던 점

### 7-1. 차단 측 대응

차단 측은 초기에는 URL/DNS 차단을 사용했고, HTTPS가 보편화된 뒤에는 SNI 필드를 확인하는 방식으로 넘어갔다. 이후 ECH/ESNI가 등장하면서 SNI 기반 차단이 어려워지자, 2026년에는 Cloudflare 같은 CDN 사업자에게 법적 요구를 보내 특정 사이트 접근을 제한하도록 하는 방식이 부각됐다.

이 방식은 기존 warning.or.kr 리다이렉트보다 명확하다. 사용자는 HTTP 451 응답을 통해 “법적 사유로 접근이 제한됐다”는 사실을 알 수 있다. 네트워크 중간에서 연결을 끊거나 우회적으로 차단하는 방식보다 차단 주체와 사유가 더 드러난다는 점은 장점이다.

### 7-2. 사용자와 서비스 측 대응

사용자 측에서는 DNS 변경, VPN, ESNI/ECH 지원 브라우저 사용처럼 여러 우회 방법이 등장했다. 서비스 운영자 입장에서는 Cloudflare 같은 CDN을 사용하면서 ECH를 켜면 SNI 기반 검열을 어느 정도 피할 수 있었다.

하지만 2026년처럼 CDN 사업자 자체가 차단 요청을 받는 구조가 되면, 기술적 우회만으로는 한계가 생긴다. 네트워크 계층에서 숨기는 방식이 통하더라도, 서비스 제공 계층에서 접근을 막으면 사용자는 결국 HTTP 451 응답을 받게 된다.

### 7-3. 미흡했던 점

- **기술적 투명성 부족:** 어떤 기준과 절차로 차단 대상이 정해졌는지 일반 이용자가 확인하기 어렵다.
- **과잉 차단 가능성:** CDN이나 IP 단위로 차단이 이뤄지면, 같은 인프라를 쓰는 정상 서비스까지 영향을 받을 수 있다.
- **프라이버시 논란:** SNI 차단은 사용자의 접속 도메인을 중간에서 들여다본다는 점 때문에 통신비밀 침해 논란을 피하기 어렵다.
- **우회와 차단의 반복:** 한 기술을 막으면 다른 우회 기술이 나오고, 다시 더 강한 차단이 등장하는 구조라 근본 해결이 되기 어렵다.

### 7-4. 해야 할 일

① HTTPS 본문뿐 아니라 SNI 같은 메타데이터 노출 여부 확인 / ② ECH 지원 여부 점검 / ③ CDN 의존 구조와 법적 차단 리스크 검토 / ④ 차단 정책 적용 시 과잉 차단 여부 모니터링 / ⑤ 사용자에게 차단 사유와 이의제기 절차를 명확히 제공

## 08 정리

한국의 인터넷 차단은 URL·DNS 차단에서 SNI 필드 차단으로, 다시 ECH 시대를 맞아 Cloudflare 직접 압박으로 이어져 왔다. 사용자의 우회 기술(ESNI/ECH)과 정부의 차단 기술이 계층을 옮겨가며 맞물려 발전한 과정이다.

네트워크 보안을 공부하는 입장에서 이 사례가 흥미로웠던 건, TLS 핸드셰이크라는 익숙한 개념이 실제로 차단과 우회의 핵심 전장이 됐다는 점이었다. SNI가 왜 평문인지, ECH가 그걸 어떻게 가리는지를 이해하면 이 공방 전체가 한 줄기로 읽힌다. 기술 표준 하나의 설계가 사회 전체의 통신 환경에 어떤 영향을 주는지 보여주는 사례라고 생각한다.

다만 이 글은 다른 두 사례처럼 명확한 침해 사고라기보다는 보안 기술과 정책이 충돌한 이슈에 가깝다. 그래서 미션에서 요구하는 “사고 원인, 대응, 미흡점” 기준에 맞춰 보면, 핵심은 SNI 기반 차단의 구조적 한계와 그에 대한 대응 방식 변화라고 정리할 수 있다.
