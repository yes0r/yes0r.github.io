## 논문 정보

**제목:** AutoLabel: Automated Fine-Grained Log Labeling for Cyber Attack Dataset Generation

**학회:** USENIX Security Symposium 2025 (34th, Seattle)

**저자:** Yihao Peng, Tongxin Zhang, Jieshao Lai, Yuxuan Zhang, Yiming Wu, Hai Wan, Xibin Zhao

**소속:** Tsinghua University / University of Science and Technology of China

**키워드:** Log Labeling, Provenance Graph, APT Detection, Cyber Attack Dataset, Dependency Explosion

## 논문을 고른 이유

AI 보안 분야를 전공 방향으로 잡으면서, ML 기반 침입 탐지 시스템이 실제로 어떻게 만들어지는지 궁금해서 관련 논문을 찾아보다 보면 항상 "고품질 데이터셋이 필요하다"는 말이 나오는데, 정작 그 데이터셋을 어떻게 만드는지에 대한 연구는 거의 없었다. 이 논문은 그 공백을 파고든 연구라서 골랐다.

솔직히 말하면 제목에서 "Automated"라는 단어가 눈에 확 들어온 것도 있다. 수작업 라벨링이 얼마나 고통스러운 일인지는 CTF 포렌식 문제 하나 풀면서도 느끼는데, 실제 공격 로그 수백만 줄을 사람이 손으로 분류한다는 건 사실 비현실적이라고 생각했다.

## 문제 정의

APT(Advanced Persistent Threat) 같은 정교한 사이버 공격을 ML 모델로 탐지하려면 학습 데이터가 필요하다. 그런데 이 데이터에는 단순히 "공격이 있었다 / 없었다"가 아니라, **어떤 로그 이벤트가 공격과 관련된 것인지 세밀하게 라벨링된 정보**가 있어야 한다.

문제는 이 라벨링이 현실에서는 거의 수작업이라는 점이다. 보안 전문가가 수백만 줄의 시스템 로그를 직접 분석하면서 "이 파일 쓰기 이벤트가 공격 체인에 해당하는가?"를 하나하나 판단해야 한다. 당연히 속도도 느리고, 분석자마다 판단 기준이 달라서 일관성도 없다. 공개된 사이버 공격 데이터셋이 절대적으로 부족한 이유가 이것이다.

이 문제에는 세 가지 기술적 난관이 있다.

- 실제 환경에서는 OS 감사 로그, 애플리케이션 로그, 네트워크 트래픽 로그가 동시에 생성되는데, 이 세 가지를 하나의 공격 흐름으로 합치는 것 자체가 어렵다.

- Provenance Graph에서 공격 관련 이벤트를 추적하다 보면 무관한 프로세스까지 줄줄이 엮이는 **의존성 폭발(Dependency Explosion)** 문제가 생긴다. Apache 같은 웹 서버는 수천 개 요청을 한 프로세스에서 처리하기 때문에 특히 심하다.

- 공격 경로가 어디서 시작해서 어디서 끝나는지 정확하게 잘라내는 것이 어렵다.

기존 도구인 Kyoushi는 규칙 기반으로 파싱하는데 로그 형식이 딱 맞아야만 쓸 수 있고, 기존 데이터셋(DARPA TC 등)은 라벨 품질이 들쭉날쭉하거나 아예 없는 경우가 많다.

## 핵심 아이디어

이 논문의 핵심 발상은 "사후에 로그를 분석해서 공격을 찾으려 하지 말고, **공격이 일어나는 순간부터 구분할 수 있는 흔적을 미리 심어 두자**"는 것이다.

처음 읽었을 때 "그게 가능해?" 싶었는데, 생각해 보면 의외로 단순한 발상이다. 데이터셋을 만들 때는 어차피 공격을 재현(reproduce)한다. 재현 환경이니까 시스템에 원하는 걸 심어 둘 수 있다. 여기서 착안해서 OS, 애플리케이션, 공격 툴에 보조 정보(auxiliary information)를 생성하는 코드를 미리 넣어 두고, 이걸 Provenance Graph와 연결해서 공격 서브그래프를 자동으로 뽑아낸다.

두 가지 핵심 기술 기여는 다음과 같다.

- **멀티소스 로그 통합**: 감사 로그, 앱 로그, 트래픽 로그를 하나의 Provenance Graph로 합친다.

- **Attack Flag + Unit Partitioning**: 공격 시작·종료 지점을 앵커 포인트로 확정하고, 장기 실행 프로세스를 작은 실행 단위(Unit)로 쪼개서 의존성 폭발을 해소한다.

## 방법론 / 시스템 설명

### 1. 환경 계측 (Instrumentation Phase)

공격 재현 전에 세 대상을 미리 수정해 둔다.

| 수정 대상  | 어떻게                            | 왜                        |
| ------ | ------------------------------ | ------------------------ |
| OS 환경  | 감사 로그에 Attack Flag 기록 트리거 삽입   | 공격 시작·종료 시점을 명확히 표시      |
| 애플리케이션 | 비동기 실행 경계마다 실행 단위(Unit) 식별자 기록 | 의존성 폭발을 일으키는 장기 프로세스를 분리 |
| 공격 툴   | 커맨드 실행·파일명·네트워크 연결에 식별 패턴 삽입   | 공격 툴에서 비롯된 이벤트를 추적       |

이 단계가 논문에서 가장 독창적인 부분이라고 생각했다. 기존 연구들이 "이미 기록된 로그에서 공격을 찾는" 방식이었다면, AutoLabel은 처음부터 찾기 쉽게 만들어 놓고 기록하는 방식으로 문제 자체를 바꿔버렸다.

### 2. 로그 통합 (Log Relating)

세 종류의 로그를 Provenance Graph로 합치는 단계다. 감사 로그의 Thread ID와 타임스탬프를 기준으로 앱 로그를 매칭하고, TCP 연결 정보로 네트워크 트래픽 로그를 연결한다. 결과적으로 "이 패킷이 들어왔고 → 이 프로세스가 반응했고 → 이 파일이 생성됐다"는 인과 관계가 하나의 그래프에 표현된다.

### 3. 의존성 폭발 해소 (Unit Partitioning)

Apache 같은 웹 서버 프로세스는 수천 개 요청을 처리한다. 단순히 프로세스 단위로 추적하면 공격과 무관한 이벤트 수백만 개가 모두 엮인다. AutoLabel은 비동기 실행 경계를 감지해서 장기 실행 프로세스를 작은 Unit으로 쪼개고, 각 Unit이 독립적인 의존성 컨텍스트를 갖게 만든다.

기존 연구들(BEEP, MPI, Omegalog)도 비슷한 문제를 다뤘지만 각각 루프 분석 오류, 복잡한 어노테이션, 특정 로그 형식 의존 같은 한계가 있었다. AutoLabel은 하나의 비동기 라이브러리 계측으로 다양한 앱에 적용할 수 있도록 설계했다.

### 4. 앵커 기반 서브그래프 추출

Attack Flag가 심어진 위치가 앵커 포인트다. 이 지점에서 출발해 정제된 그래프 위의 인과 의존성을 따라가면, 공격 체인 전체가 서브그래프로 잘려 나온다. 이 서브그래프 안의 모든 엣지와 노드가 "공격 관련"으로 라벨링된다.

## 평가 및 결과 해석

### 실험 구성

29개 시나리오에서 평가를 진행했다. 25개 실제 CVE 취약점(12개 애플리케이션, 5개 프로그래밍 언어), MITRE CTID가 설계한 Sandworm APT 시뮬레이션, 서비스 클러스터 내 멀티-홉 공격으로 구성됐다.

### 핵심 결과

| 지표             | 결과                     |
| -------------- | ---------------------- |
| 라벨링 정확도        | **100%** (전체 29개 시나리오) |
| 시나리오당 최대 소요 시간 | **96분**                |
| 공개 벤치마크 데이터셋   | **580개**               |

100% 정확도라는 숫자가 처음엔 좀 과장 같았다. 그런데 보조 정보 기반의 앵커 포인트가 확정적으로 공격 경계를 지정하기 때문에 이론적으로 라벨 오류가 개입할 여지가 없다는 걸 이해하고 나니 납득됐다. 다만 이건 앵커 포인트가 정확하게 심어진 경우에만 성립한다는 전제가 있다.

멀티소스 로그 통합, 의존성 폭발 해소, 정밀 라벨링을 동시에 달성한 자동화 도구가 없었다는 점에서 기존 방법들과의 차이가 명확하다. 기존에 Kyoushi처럼 일부 자동화를 시도한 도구가 있었지만, 형식이 딱 맞아야 쓸 수 있다는 한계를 AutoLabel이 극복했다.

## 한계점

- **새로운 비동기 라이브러리에는 수동 계측 필요**: 하나의 비동기 라이브러리를 계측하면 여러 앱에 적용할 수 있도록 설계됐지만, 아예 새로운 비동기 모델을 쓰는 앱이 나오면 그에 맞는 커스텀 계측을 따로 만들어야 한다. 저자들도 이 자동화를 향후 과제로 남겼다.

- **통제된 재현 환경에서만 검증됨**: 실험이 연구 환경에서 이루어졌다. 실제 운영 환경에서는 노이즈 로그, 불완전한 계측 등이 영향을 줄 수 있어서, "100% 정확도"를 실제 SOC 환경에 그대로 가져가려면 별도의 강건성 검증이 필요하다.

- **공격 툴 수정이 전제됨**: 알려진 공격 도구를 사용하는 재현 시나리오에는 자연스럽지만, 완전히 새로운 공격 방식이나 수정하기 어려운 공격 프레임워크에는 적용이 어렵다.

- **Windows 환경 미검증**: 공개된 실험은 Linux 기반이다. Windows 감사 로그 구조(ETW, EVTX 등)는 다르기 때문에, 엔터프라이즈 환경에서 실질적으로 쓰이는 Windows에서의 적용 가능성은 별도 확인이 필요하다.

## 느낀 점

읽기 전에는 솔직히 "로그 라벨링이 논문 주제가 될 만큼 어려운 문제인가?" 싶었다. 읽고 나서는 생각이 완전히 바뀌었다.

보안 AI 관련 논문들을 보면 항상 "더 좋은 탐지 모델"을 만드는 데 초점이 맞춰져 있는데, 이 논문은 그 전 단계를 파고들었다. 모델이 아무리 좋아도 훈련 데이터가 부실하면 결과도 부실하다. 데이터 품질 문제를 풀지 않으면 탐지 성능은 결국 한계에 부딪히는데, 이 지점을 직접 건드린 연구라는 게 인상적이었다.

특히 "사후 분석"이 아닌 사전 계측으로 문제를 바꾼 발상이 좋았다. 어떤 문제를 더 어렵게 풀려는 대신, 문제 자체를 더 풀기 쉬운 형태로 바꿔서 푼다는 접근 방식. 이게 보안 연구뿐만 아니라 다른 분야에서도 쓸 수 있는 사고방식이라는 생각이 들었다.

그리고 580개의 벤치마크 데이터셋을 공개한다는 점도 중요하다. 지금까지 APT 탐지 연구들이 데이터셋 부족으로 고통받아 왔는데, 이게 진짜로 공개되면 후속 연구들의 베이스라인이 달라질 수 있다고 본다.

## 앞으로 해볼 것

### 더 읽어볼 논문

- **BEEP, MPI, Omegalog, Alchemist** — AutoLabel이 비교 대상으로 언급한 의존성 폭발 해소 선행 연구들. AutoLabel이 왜 기존 방식보다 낫다고 주장하는지 직접 확인해 보고 싶다.

- **MAGIC (USENIX Security '24)** — Masked Graph Representation Learning 기반 APT 탐지. AutoLabel로 만든 데이터셋이 이런 탐지 모델 학습에 어떻게 연결되는지 흐름을 이어 보고 싶다.

- **DARPA TC 데이터셋 관련 논문들** — 기존 데이터셋의 한계가 어떻게 지적돼 왔는지 맥락을 잡기 위해.

### 비슷한 문제를 다른 분야에 적용한다면

- **클라우드 네이티브 환경** — 컨테이너, 쿠버네티스 환경에서 Provenance Graph가 어떻게 달라지는지 궁금하다. 마이크로서비스 아키텍처에서는 서비스 간 경계가 훨씬 많아서 멀티-홉 공격 추적이 더 복잡해질 텐데, AutoLabel 방식이 그대로 통할지.

- **AI 모델 훈련 파이프라인 보안** — 요즘 관심 갖고 있는 AI 보안 분야와 연결해서, 모델 학습 과정에서 일어나는 공격(데이터 포이즈닝, 모델 탈취 등)을 로그로 추적하고 라벨링하는 방향으로 적용할 수 있을지 생각해 보고 싶다.

### 직접 구현·재현해 보고 싶은 것

- 논문이 공개하는 580개 벤치마크 데이터셋을 받아서 간단한 GNN 기반 탐지 모델을 직접 붙여 보는 실험. 데이터셋 품질이 탐지 성능에 실제로 얼마나 영향을 미치는지 숫자로 확인해 보고 싶다.

- `auditd`로 간단한 공격 시나리오를 직접 재현하고 Provenance Graph를 시각화해 보는 것. 의존성 폭발이 실제로 어떻게 생기는지 눈으로 봐야 이해가 빠를 것 같다.

### 연구/프로젝트로 발전시킨다면

- **Windows ETW 이식** — 논문이 명시적으로 남긴 한계인데, 엔터프라이즈 보안에서는 Windows가 훨씬 중요한 환경이다. AutoLabel의 계측 코드를 ETW(Event Tracing for Windows)에 이식하면 Windows 기반 APT 탐지 데이터셋을 만들 수 있다.

- **LLM 기반 앵커 포인트 자동 생성** — 지금은 공격 시나리오를 사람이 설계하면서 어디에 Attack Flag를 심을지 정한다. LLM이 MITRE ATT&CK 프레임워크를 참고해서 공격 시나리오를 자동으로 설계하고 계측 위치까지 제안한다면, 데이터셋 생성 전체가 훨씬 더 자동화될 것 같다. 관심 있는 AI 보안 분야와도 맞닿아 있어서 흥미로운 방향이다.
