## 논문 정보

**제목:** AutoLabel: Automated Fine-Grained Log Labeling for Cyber Attack Dataset Generation

**학회:** USENIX Security Symposium 2025 (34th, Seattle)

**저자:** Yihao Peng, Tongxin Zhang, Jieshao Lai, Yuxuan Zhang, Yiming Wu, Hai Wan, Xibin Zhao

**소속:** Tsinghua University / University of Science and Technology of China

**키워드:** Log Labeling, Provenance Graph, APT Detection, Cyber Attack Dataset, Dependency Explosion

## 논문을 고른 이유

AI 보안 분야를 전공 방향으로 잡으면서, ML 기반 침입 탐지 시스템이 실제로 어떻게 만들어지는지 궁금해서 관련 논문을 찾아보다 보면 항상 "고품질 데이터셋이 필요하다"는 말이 나오는데, 정작 그 데이터셋을 어떻게 만드는지에 대한 연구는 거의 없었다. 이 논문은 그 공백을 파고든 연구라서 골랐다.

솔직히 말하면 제목에서 "Automated"라는 단어가 눈에 확 들어온 것도 있다. 수작업 라벨링이 얼마나 고통스러운 일인지는 CTF 포렌식 문제 하나 풀면서도 느끼는데, 실제 공격 로그 수백만 줄을 사람이 손으로 분류한다는 건 사실 비현실적이라고 생각했다.

## 문제 정의

APT(Advanced Persistent Threat)는 공격자가 오랫동안 탐지를 피하면서 시스템 내부에서 조용히 활동하는 유형의 공격이다. 일반적인 악성코드 탐지처럼 서명 기반으로는 잡을 수 없어서, 최근 연구들은 시스템 로그 기반의 ML 모델로 탐지하려는 방향을 많이 택하고 있다.

그런데 ML 모델을 제대로 훈련시키려면 학습 데이터가 필요하다. 단순히 "공격이 있었다 / 없었다"가 아니라, **수백만 개의 로그 이벤트 중에서 어느 것이 공격과 관련된 것인지 이벤트 단위로 라벨링된 데이터**가 있어야 한다. 프로세스가 어떤 파일을 읽었고, 어떤 네트워크 연결을 열었고, 어떤 자식 프로세스를 생성했는지 — 이 각각의 이벤트가 공격 체인의 일부인지 아닌지를 전부 구분해 놔야 한다.

이게 현실에서는 거의 수작업이다. 보안 전문가가 수백만 줄의 로그를 직접 분석하면서 하나하나 판단해야 한다. 당연히 속도도 느리고, 분석자마다 기준이 달라서 일관성도 없다. 그러다 보니 공개된 고품질 사이버 공격 데이터셋은 절대적으로 부족하고, 있는 것(DARPA TC 등)도 라벨이 거칠거나 아예 없는 경우가 많다.

### 왜 자동화가 이렇게 어려운가

"로그 파일을 파싱해서 공격 키워드를 찾으면 되는 거 아닌가?" 싶을 수 있는데, 실제로는 세 가지 기술적 난관이 있다.

- **멀티소스 로그 통합 문제.** 실제 환경에서는 OS 감사 로그(auditd 등), 애플리케이션 로그(Apache access log 등), 네트워크 트래픽 로그가 동시에 생성된다. 문제는 이 세 가지가 서로 다른 형식, 다른 타임스탬프 정밀도, 다른 식별자를 쓴다는 점이다. "이 HTTP 요청이 감사 로그의 어느 프로세스 이벤트와 연결되는가"를 자동으로 연결하는 게 생각보다 까다롭다.

- **의존성 폭발(Dependency Explosion) 문제.** 공격이 어느 프로세스를 통해 진행됐는지 추적하려면 Provenance Graph를 쓴다. Provenance Graph는 "프로세스 A가 파일 B를 읽었다", "프로세스 A가 프로세스 C를 생성했다"처럼 시스템 이벤트를 노드와 엣지로 표현한 그래프다. 이 그래프에서 공격과 관련된 노드를 찾아 거슬러 올라가다 보면, 실제 공격과 무관한 프로세스까지 줄줄이 엮이는 현상이 생긴다. Apache 같은 웹 서버가 특히 심한데, 수천 개의 요청을 같은 프로세스에서 처리하기 때문에 공격 요청 하나가 나머지 모든 정상 요청과 같은 프로세스 노드를 공유하게 된다. 결과적으로 거의 모든 이벤트가 "공격 관련"으로 분류돼버린다.

- **공격 경계 추출 문제.** 의존성 폭발을 해소해도, 결국 Provenance Graph에서 공격 체인이 어디서 시작해서 어디서 끝나는지를 정확하게 잘라내야 한다. 이걸 자동으로 하는 방법이 마땅히 없었다.

기존 도구인 Kyoushi는 멀티소스 로그를 규칙 기반으로 파싱하는데, 로그 형식이 딱 맞아야만 적용할 수 있고 새로운 환경에 쓰려면 규칙을 처음부터 다시 짜야 한다. 결국 범용적으로 쓸 수 있는 자동화 라벨링 도구가 없는 상태였다.

## 핵심 아이디어

이 논문의 핵심 발상은 "사후에 로그를 분석해서 공격을 찾으려 하지 말고, **공격이 일어나는 순간부터 구분할 수 있는 흔적을 미리 심어 두자**"는 것이다.

처음 읽었을 때 "그게 가능해?" 싶었는데, 생각해 보면 의외로 단순한 발상이다. 데이터셋을 만들 때는 어차피 공격을 재현(reproduce)한다. 재현 환경이니까 시스템에 원하는 걸 심어 둘 수 있다. 여기서 착안해서 OS, 애플리케이션, 공격 툴에 보조 정보(auxiliary information)를 생성하는 코드를 미리 넣어 두고, 이걸 Provenance Graph와 연결해서 공격 서브그래프를 자동으로 뽑아낸다.

두 가지 핵심 기술 기여는 다음과 같다.

- **멀티소스 로그 통합**: 감사 로그, 앱 로그, 트래픽 로그를 하나의 Provenance Graph로 합친다.

- **Attack Flag + Unit Partitioning**: 공격 시작·종료 지점을 앵커 포인트로 확정하고, 장기 실행 프로세스를 작은 실행 단위(Unit)로 쪼개서 의존성 폭발을 해소한다.

USENIX Security '25 저자 발표를 보면서 이 논문이 문제를 어떻게 재정의했는지가 더 명확하게 와닿았다. 저자가 강조한 부분은 "개별 로그 항목을 하나하나 보는 게 아니라, 시스템 전체의 행동을 Provenance Graph로 보자"는 시각의 전환이었다. 공격을 그래프 위의 인과적으로 연결된 이벤트 묶음으로 보면, 라벨링 문제가 "어느 로그가 공격인가"에서 "공격 서브그래프를 어떻게 정확하게 잘라내는가"로 바뀐다. 문제 자체를 더 풀기 쉬운 형태로 바꾼 거다.

처음엔 "그냥 규칙 기반으로 공격 키워드 찾으면 안 되나?" 싶었는데, USENIX Security '25 저자 발표에서 기존 방식들의 한계를 보고 이해가 됐다. 시간 창 기반 방식은 특정 시간 내 활동을 싸잡아 라벨링해서 정확도가 떨어지고, 탐지 도구 기반 방식은 탐지 도구가 보는 것만 볼 수 있어서 본질적으로 불완전하고, 규칙 매칭은 조금만 변형돼도 깨진다. 세 방식 다 "이미 기록된 것에서 찾는다"는 한계를 공유한다. AutoLabel은 그 전 단계, 즉 공격이 일어나는 순간에 개입해서 나중에 찾기 쉬운 흔적을 남겨두는 방식으로 이 한계를 통째로 우회한다.

## 위협 모델 및 공격 흐름

AutoLabel이 다루는 공격은 APT, 즉 Advanced Persistent Threat다. 서명 기반 탐지를 피하면서 오랫동안 내부에 숨어 활동하는 유형의 공격인데, 논문에서 상정하는 위협 모델은 이런 공격을 데이터셋으로 재현할 수 있는 환경을 전제로 한다. 구체적으로는 세 가지를 가정한다.

- **감사 시스템은 신뢰할 수 있다.** 공격자가 auditd 같은 감사 로그 수집 시스템 자체를 조작하지는 않는다고 가정한다. 로그 위변조까지 고려하면 라벨링의 전제 자체가 무너지기 때문에, 이건 이 분야 연구 전반에서 공통적으로 쓰는 가정이다.

- **공격은 재현 가능한 형태로 정의되어 있다.** CVE로 등록된 취약점 또는 MITRE ATT&CK 기반의 시나리오처럼, 재현 스크립트나 공격 툴이 존재하는 공격을 대상으로 한다. 완전히 새로운 제로데이를 즉석에서 생성하는 상황은 아니다.

- **공격자는 외부에서 네트워크를 통해 침입한다.** 내부자 공격이나 물리적 접근은 포함하지 않는다. 취약한 서비스를 통한 초기 침입 → 권한 상승 → 횡적 이동 → 데이터 탈취의 흐름이 기본 공격 모델이다.

### 공격 흐름이 어떻게 생겼는가

논문에서 실제로 재현한 공격들의 전형적인 흐름을 정리하면 이렇다. APT 공격은 보통 여러 단계를 거치는데, 각 단계마다 시스템 로그에 흔적이 남는다.

| 단계         | 공격자 행동                     | 시스템 로그에 남는 흔적                      |
| ---------- | -------------------------- | ---------------------------------- |
| 초기 침입      | 취약한 웹 서비스 또는 CVE 취약점 익스플로잇 | 네트워크 연결 이벤트, 비정상적인 HTTP 요청         |
| 코드 실행      | 원격 코드 실행(RCE)으로 셸 획득       | 웹 서버 프로세스가 자식 프로세스(sh, bash 등) 생성  |
| 정찰 / 권한 상승 | 시스템 정보 수집, 권한 상승 시도        | passwd, shadow 파일 읽기, suid 바이너리 실행 |
| 횡적 이동      | 내부 네트워크의 다른 호스트로 이동        | 내부 IP로의 새 TCP 연결, SSH 또는 SMB 이벤트   |
| 데이터 탈취     | 민감 파일 읽기 및 외부 전송           | 파일 읽기 이벤트 + 외부 IP로의 네트워크 전송        |

문제는 이 흔적들이 수백만 개의 정상 이벤트 사이에 섞여 있다는 점이다. 웹 서버가 자식 프로세스를 생성하는 건 정상 동작이기도 하고, 파일을 읽는 이벤트도 정상 요청에서도 수도 없이 발생한다. Provenance Graph를 그려 보면, 공격 체인이 이 정상 이벤트들과 같은 프로세스 노드를 공유하고 있어서 공격과 관련 없는 이벤트 수백만 개가 함께 딸려오게 된다. 이게 의존성 폭발 문제의 실체다.

### Sandworm 시뮬레이션 시나리오

논문이 가장 복잡한 평가 시나리오로 사용한 게 MITRE CTID가 설계한 Sandworm APT 시뮬레이션이다. Sandworm은 러시아 GRU 소속으로, 우크라이나 전력망 공격이나 NotPetya 랜섬웨어로 알려진 실제 위협 그룹이다. MITRE가 이 그룹의 TTPs(Tactics, Techniques, Procedures)를 기반으로 시뮬레이션 시나리오를 설계했다. 피싱 첨부파일로 초기 접근하고, 웹셸을 디스크에 쓰고, 내부 도메인을 탐색하고, 패스워드 스프레이로 횡적 이동을 시도하고, 최종적으로 데이터를 압축해서 C2 채널로 탈취하는 흐름이다.

이런 멀티-스텝 공격은 한 호스트에서 끝나지 않기 때문에 라벨링이 특히 어렵다. 논문의 멀티-홉 공격 실험은 26개 노드 클러스터에서 10번의 호스트 간 이동을 포함했는데, AutoLabel은 이 시나리오에서도 정확하게 공격 관련 이벤트만 라벨링하는 데 성공했다고 한다. 이게 단순 CVE 재현이 아니라 실제 APT 흐름 전체를 커버할 수 있다는 증거가 되는 부분이다.

## 방법론 / 시스템 설명

AutoLabel은 크게 두 단계로 나뉜다. 공격 재현 전에 환경을 준비하는 **계측 단계(Instrumentation Phase)**와, 재현 후 로그를 처리해서 라벨을 만드는 **라벨링 단계(Labeling Phase)**다. 라벨링 단계는 다시 로그 통합 → 그래프 정제 → 서브그래프 추출의 순서로 진행된다.

### 1. 환경 계측 (Instrumentation Phase)

공격을 재현하기 전에 세 가지 대상을 미리 수정해 둔다.

| 수정 대상  | 어떻게                            | 왜                             |
| ------ | ------------------------------ | ----------------------------- |
| OS 환경  | 감사 로그에 Attack Flag 기록 트리거 삽입   | 공격 시작·종료 시점을 명확히 표시하기 위해      |
| 애플리케이션 | 비동기 실행 경계마다 실행 단위(Unit) 식별자 기록 | 의존성 폭발을 일으키는 장기 프로세스를 분리하기 위해 |
| 공격 툴   | 커맨드 실행·파일명·네트워크 연결에 식별 패턴 삽입   | 공격 툴에서 비롯된 이벤트를 나중에 추적하기 위해   |

이 단계가 논문에서 가장 독창적인 부분이라고 생각했다. 기존 연구들이 "이미 기록된 로그에서 공격을 찾는" 방식이었다면, AutoLabel은 처음부터 찾기 쉽게 만들어 놓고 기록하는 방식으로 문제 자체를 바꿔버렸다.

예를 들어 공격 툴을 수정하는 부분을 보면, 공격자가 원격에서 실행하는 커맨드 앞뒤에 고유한 식별 문자열을 붙여 둔다. 그러면 나중에 감사 로그에서 그 문자열을 포함한 이벤트를 찾으면 "이게 공격 툴이 만들어낸 이벤트다"라는 걸 자동으로 알 수 있다. 사람이 눈으로 훑으면서 찾는 게 아니라, 공격이 일어나는 순간부터 이미 구분이 돼 있는 거다.

### 2. 로그 통합 (Log Relating)

계측된 환경에서 공격을 재현하고 나면 세 종류의 로그가 생긴다. 이걸 하나의 Provenance Graph로 합치는 단계다.

감사 로그와 애플리케이션 로그를 연결할 때는 Thread ID와 타임스탬프를 기준으로 매칭한다. 감사 로그는 syscall 단위로 이벤트를 기록하는데, 앱 로그 이벤트를 가장 가까운 syscall 타임스탬프에 대응시키는 방식이다. 네트워크 트래픽 로그는 TCP 연결 정보(소스 IP·포트, 목적지 IP·포트)를 기준으로 감사 로그의 `connect()`, `accept()` syscall 이벤트와 연결한다.

결과적으로 "외부에서 이 HTTP 요청이 들어왔고 → Apache 프로세스가 반응했고 → 특정 파일을 읽었고 → 자식 프로세스를 생성했다"는 인과 관계가 하나의 그래프 안에 전부 표현된다. 세 소스에 흩어져 있던 정보가 하나의 공격 흐름으로 연결되는 것이다.

### 3. 의존성 폭발 해소 (Unit Partitioning)

로그를 합쳐서 그래프를 만들고 나면 의존성 폭발 문제가 바로 나타난다. Apache 웹 서버 프로세스를 예로 들면, 하나의 프로세스가 수천 개의 요청을 처리하기 때문에 그래프 상에서 정상 요청과 공격 요청이 전부 같은 프로세스 노드에 연결되어 있다. 공격과 관련된 엣지를 찾으려고 프로세스 노드에서 뻗어 나가면, 공격과 전혀 무관한 수백만 개의 이벤트가 모두 딸려온다.

AutoLabel의 해법은 장기 실행 프로세스를 **실행 단위(Unit)**로 쪼개는 것이다. 비동기 프로그래밍에서는 하나의 요청을 처리하는 코드 블록이 시작되고 끝나는 경계가 있다. 계측 단계에서 애플리케이션 코드에 이 경계를 기록하는 코드를 심어 뒀기 때문에, 로그에는 "여기서 새 Unit 시작", "여기서 Unit 종료" 마커가 찍혀 있다. AutoLabel은 이 마커를 기준으로 프로세스를 여러 개의 독립적인 Unit으로 분리한다. 각 Unit은 자신이 처리한 요청에 관련된 이벤트만 갖게 되므로 의존성이 극적으로 줄어든다.

기존 연구들도 비슷한 시도를 했다. BEEP은 루프와 메모리 의존성을 분석해서 분리하려 했지만 잘못된 분리가 생기는 문제가 있었고, MPI는 데이터 구조 어노테이션이 필요해서 복잡했다. Omegalog과 Alchemist는 앱 로그를 활용하지만 특정 로그 내용과 형식에 의존해서 범용성이 떨어졌다. AutoLabel은 하나의 비동기 라이브러리를 계측하면 그 라이브러리를 쓰는 여러 앱에 동일하게 적용할 수 있어서, 기존 방법보다 범용성이 높다.

### 4. 앵커 기반 서브그래프 추출

의존성을 정제한 그래프에서 이제 실제 공격 경로를 잘라낸다. 여기서 계측 단계에서 심어 둔 Attack Flag가 역할을 한다. Attack Flag가 찍힌 이벤트가 **앵커 포인트(Anchor Point)**가 되는데, 이 지점이 "공격이 이 이벤트를 만들었다"는 확실한 단서다.

앵커 포인트에서 출발해서 정제된 그래프 위의 인과 의존성을 따라가면, 공격 체인 전체를 하나의 서브그래프로 뽑아낼 수 있다. 이 서브그래프 안의 모든 노드와 엣지가 "공격 관련(malicious)"으로, 나머지는 "정상(benign)"으로 라벨링된다. 사람이 판단하는 게 아니라 앵커 포인트로부터의 의존성 추적이 자동으로 경계를 결정하기 때문에, 분석자마다 결과가 달라지는 문제가 없다.

## 평가 및 결과 해석

### 실험 구성

29개 시나리오에서 평가를 진행했다. 구성이 꽤 다양한데, 25개 실제 CVE 취약점(12개 애플리케이션, C·Python·Go·PHP·Java 5개 언어), MITRE CTID가 설계한 Sandworm APT 시뮬레이션, 서비스 클러스터 내 멀티-홉 공격이 포함됐다. 단일 애플리케이션뿐만 아니라 여러 서비스가 연결된 복합 환경도 실험했다는 점에서 꽤 실제 환경에 가까운 조건이라고 봤다.

그리고 실험에 쓴 CVE들이 Apache, Redis, PHP 같은 실제로 많이 쓰이는 소프트웨어의 취약점이라는 점도 중요하다. 연구자들이 임의로 만든 가상의 취약점이 아니라, 실제로 공격에 쓰였거나 쓰일 수 있는 것들이다.

### 핵심 결과

| 지표             | 결과                     |
| -------------- | ---------------------- |
| 라벨링 정확도        | **100%** (전체 29개 시나리오) |
| 시나리오당 최대 소요 시간 | **96분**                |
| 공개 벤치마크 데이터셋   | **580개**               |

100% 정확도라는 숫자가 처음엔 좀 과장 같았다. 실제로 읽다 보니 이게 왜 가능한지 이해됐다. AutoLabel이 생성하는 라벨은 "앵커 포인트에서 인과 의존성을 따라간 결과"이기 때문에 사람의 판단이 개입하지 않는다. 라벨 정확도를 평가한 방식도 연구팀이 직접 각 시나리오의 정답을 수작업으로 만들어 두고, AutoLabel이 생성한 라벨과 비교하는 방식이었다. 29개 시나리오 전부에서 차이가 없었다는 뜻이다. 다만 이건 앵커 포인트 자체가 올바르게 심어졌다는 전제 위에서 성립하고, 계측이 불완전하면 정확도도 깨질 수 있다.

96분이라는 숫자는 멀티-홉 공격처럼 복잡한 시나리오에서의 최대치다. 단순한 시나리오는 훨씬 빠르다. 기존에 수작업으로 하면 보안 전문가가 하루 이상 투자해야 하는 작업이 최대 한 시간 반 안에 자동으로 완료된다는 게 실질적인 의미다.

580개의 벤치마크 데이터셋을 공개한다는 점도 결과 중 하나로 봐야 한다. 논문 자체의 성과이기도 하지만, 이게 공개되면 이후 APT 탐지 모델 연구들이 공통 기반 위에서 비교·평가를 할 수 있게 된다. 지금까지 데이터셋이 없어서 재현이 어렵고 비교가 힘들었던 문제가 일부 해소될 수 있다.

## 한계점

- **새로운 비동기 라이브러리에는 수동 계측 필요**: 하나의 비동기 라이브러리를 계측하면 여러 앱에 적용할 수 있도록 설계됐지만, 아예 새로운 비동기 모델을 쓰는 앱이 나오면 그에 맞는 커스텀 계측을 따로 만들어야 한다. 저자들도 이 자동화를 향후 과제로 남겼다.

- **통제된 재현 환경에서만 검증됨**: 실험이 연구 환경에서 이루어졌다. 실제 운영 환경에서는 노이즈 로그, 불완전한 계측 등이 영향을 줄 수 있어서, "100% 정확도"를 실제 SOC 환경에 그대로 가져가려면 별도의 강건성 검증이 필요하다.

- **공격 툴 수정이 전제됨**: 알려진 공격 도구를 사용하는 재현 시나리오에는 자연스럽지만, 완전히 새로운 공격 방식이나 수정하기 어려운 공격 프레임워크에는 적용이 어렵다.

- **Windows 환경 미검증**: 공개된 실험은 Linux 기반이다. Windows 감사 로그 구조(ETW, EVTX 등)는 다르기 때문에, 엔터프라이즈 환경에서 실질적으로 쓰이는 Windows에서의 적용 가능성은 별도 확인이 필요하다.

## 느낀 점

읽기 전에는 솔직히 "로그 라벨링이 논문 주제가 될 만큼 어려운 문제인가?" 싶었다. 읽고 나서는 생각이 완전히 바뀌었다.

보안 AI 관련 논문들을 보면 항상 "더 좋은 탐지 모델"을 만드는 데 초점이 맞춰져 있는데, 이 논문은 그 전 단계를 파고들었다. 모델이 아무리 좋아도 훈련 데이터가 부실하면 결과도 부실하다. 데이터 품질 문제를 풀지 않으면 탐지 성능은 결국 한계에 부딪히는데, 이 지점을 직접 건드린 연구라는 게 인상적이었다.

특히 "사후 분석"이 아닌 사전 계측으로 문제를 바꾼 발상이 좋았다. 어떤 문제를 더 어렵게 풀려는 대신, 문제 자체를 더 풀기 쉬운 형태로 바꿔서 푼다는 접근 방식. 이게 보안 연구뿐만 아니라 다른 분야에서도 쓸 수 있는 사고방식이라는 생각이 들었다.

그리고 580개의 벤치마크 데이터셋을 공개한다는 점도 중요하다. 지금까지 APT 탐지 연구들이 데이터셋 부족으로 고통받아 왔는데, 이게 진짜로 공개되면 후속 연구들의 베이스라인이 달라질 수 있다고 본다.

## 앞으로 해볼 것

### 더 읽어볼 논문

- **BEEP, MPI, Omegalog, Alchemist** — AutoLabel이 비교 대상으로 언급한 의존성 폭발 해소 선행 연구들. AutoLabel이 왜 기존 방식보다 낫다고 주장하는지 직접 확인해 보고 싶다.

- **MAGIC (USENIX Security '24)** — Masked Graph Representation Learning 기반 APT 탐지. AutoLabel로 만든 데이터셋이 이런 탐지 모델 학습에 어떻게 연결되는지 흐름을 이어 보고 싶다.

- **DARPA TC 데이터셋 관련 논문들** — 기존 데이터셋의 한계가 어떻게 지적돼 왔는지 맥락을 잡기 위해.

### 비슷한 문제를 다른 분야에 적용한다면

- **클라우드 네이티브 환경** — 컨테이너, 쿠버네티스 환경에서 Provenance Graph가 어떻게 달라지는지 궁금하다. 마이크로서비스 아키텍처에서는 서비스 간 경계가 훨씬 많아서 멀티-홉 공격 추적이 더 복잡해질 텐데, AutoLabel 방식이 그대로 통할지.

- **AI 모델 훈련 파이프라인 보안** — 요즘 관심 갖고 있는 AI 보안 분야와 연결해서, 모델 학습 과정에서 일어나는 공격(데이터 포이즈닝, 모델 탈취 등)을 로그로 추적하고 라벨링하는 방향으로 적용할 수 있을지 생각해 보고 싶다.

### 직접 구현·재현해 보고 싶은 것

- 논문이 공개하는 580개 벤치마크 데이터셋을 받아서 간단한 GNN 기반 탐지 모델을 직접 붙여 보는 실험. 데이터셋 품질이 탐지 성능에 실제로 얼마나 영향을 미치는지 숫자로 확인해 보고 싶다.

- `auditd`로 간단한 공격 시나리오를 직접 재현하고 Provenance Graph를 시각화해 보는 것. 의존성 폭발이 실제로 어떻게 생기는지 눈으로 봐야 이해가 빠를 것 같다.

### 연구/프로젝트로 발전시킨다면

- **Windows ETW 이식** — 논문이 명시적으로 남긴 한계인데, 엔터프라이즈 보안에서는 Windows가 훨씬 중요한 환경이다. AutoLabel의 계측 코드를 ETW(Event Tracing for Windows)에 이식하면 Windows 기반 APT 탐지 데이터셋을 만들 수 있다.

- **LLM 기반 앵커 포인트 자동 생성** — 지금은 공격 시나리오를 사람이 설계하면서 어디에 Attack Flag를 심을지 정한다. LLM이 MITRE ATT&CK 프레임워크를 참고해서 공격 시나리오를 자동으로 설계하고 계측 위치까지 제안한다면, 데이터셋 생성 전체가 훨씬 더 자동화될 것 같다. 관심 있는 AI 보안 분야와도 맞닿아 있어서 흥미로운 방향이다.
