### SQLI이란?

웹 입력값을 이용해서 데이터베이스 쿼리를 조작하는 공격으로, 사용자의 입력을 믿고 SQL문으로 만들어 생기는 취약점입니다.





쿼리 구조, 기본 명령어, 공격 유형, 실습, 보안관점으로 이 SQLI에 대해 알아보겠습니다





먼저 SQL의 쿼리 구조는 SQL 문장의 형태, 뼈대 정도로 생각하면 됩니다!





- FROM → 어디서 가져오기

- WHERE → 조건

- UNION → 결과 합치기

- OR / AND → 조건 연결

- SELECT → 데이터 가져오기

등의 명령어를 조합해서 쿼리 구조를 짜게 되는데, 기본 구조로는



SELECT 컬럼
FROM 테이블
WHERE 조건



이 합쳐진



```
SELECT * FROM users
WHERE id = '입력값' AND password = '입력값';
```



이런 구조가 있습니다! SQLI는 이 쿼리 구조 안에 내 코드를 끼워 넣어서 원래 의도를 바꿔버리는 공격 기법입니다.



이 입력값이, 데이터가 아니라 코드처럼 해석이 될 때 SQLI가 발생하게 되는데 모든 값이 위험한 것이 아니라 원래 의도대로 일반 데이터를 넣으면 안전하겠지만, 이곳에 id: ' OR 1=1 -- 같은 입력값을 넣어버리면



SQL내에서는

WHERE id = '' OR 1=1 --'

로 처리가 되어서, 문자열이 닫히고 새로운 조건이 추가되며 뒤의 입력값이 그냥 무시되는 사건이 일어날 수가 있습니다

즉, 데이터로 들어와야 할 입력값이 SQL 명령어로 바뀌게 되는 것이죠. 단순히 입력값이 들어가서가 아니라 입력값이 쿼리 구조를 바꿔버리게 되는 것입니다.







다음으로 기본 명령어에 대해 알아보겠습니다.



기본 명령어는



- SELECT → 데이터 가져오기

- WHERE → 조건 조작(조건 걸기)

- OR 1=1, AND→ 인증 우회(조건 연결)

- -- → 뒤 내용 삭제(주석)

- UNION → 데이터 탈취(두 결과 합치기)

- SUBSTRING / ASCII → 한 글자씩 추출

- SLEEP → 시간 기반 공격(시간 지연)

이정도만 알아도 충분한데, 이후 UNION을 이용한 SQLI에 대해 설명할 것이기 떄문에 UNION만 조금 더 설명을 하면,



```
SELECT username FROM users
UNION
SELECT password FROM users;
```



이런식으로 써 DB의 데이터를 직접 출력할 떄 사용하는 SQLI 핵심 기술 중 하나로 사용됩니다.





이어서, 공격 유형에 대해 말해보자면 굉장히 여러개가 있는데 데이터를 보여주는지, 반응이 있는지 등에 따라 공격유형이 달라질 수가 있습니다.



제일 먼저 Login bypass에 대해 먼저 알아보면 '비밀 번호를 몰라도 로그인을 통과하게 만드는 공격'으로,



```
SELECT * FROM users
WHERE id = '입력값' AND password = '입력값';
```



이렇게 로그인이 되어 있으면, 서버 입장에선 결과가 1개라도 나오면 로그인이 성공되기 때문에 WHERE 조건이 무조건 TRUE가 되게 만들자는 아이디어에서 출발한 ㄱ것입니다.



가장 기본으로는 OR 1=1 공격이 있고,



입력값이

id: admin
pw: ' OR 1=1 --

일때



실제 쿼리는

```
SELECT * FROM users
WHERE id='admin' AND password='' OR 1=1 --'
```

으로 작동되기 때문에 1=1으로 항상 트루. 전체 조건이 트루가 되므로 로그인이 성공되는 방식입니다.





다음으로는 Union-based가 있는데, UNION은 A결과 + B결과로 만들어주는 +(연결점) 역할을 하고 있기 때문에 결과를 합치게 만들어줍니다. 이것을 이용한 공격인데, 이걸 이용해서 원래 안 보여주는 데이터를 화면에 띄우게 될 수가 있습니다.



원래 쿼리가

```
SELECT id, name FROM users WHERE id='1';
```

결과는 1 | yeseul로 나온다면,



공격을 입력하여

```
SELECT id, name FROM users WHERE id='1'
UNION SELECT username, password FROM admin
```

로 만들어서



1 | yeseul
admin | 1234

라는 결과를 만들어내는 것입니다,



이게 되는 이유는, 서버는 그냥 DB에서 받은 데이터를 화면에 출력하기 때문에 UNION으로 끼워넣은 데이터도 그대로 출력하기 때문입니다.



이쯤되면 이걸 어떻게 꺼내오지? 그냥 내가 데이터를 추가한 것 뿐인데 어떻게 이런 결과가 나오지? 라는 생각이 들 수 있는데, DB에선 그냥 결과를 정상 동작처럼 처리하고, 서버 입장에선 어디서 온 데이터인지 안 보기 때문에 공격이 성공되는 것입니다.



UNION의 목적은, 가짜 행을 넣는 로그인 우회도 있지만 DB에 있는 진짜 데이터를 가져오는 것이 크기 때문에 본질은 데이터 조회의 범위를 확장하는 것입니다. UNION을 이용하면, 유저이름, 패스워드, 이메일, DB이름, 테이블 구조 등 다양한 데이터를 탈취할 수 있게 됩니다.



UNION을 사용할 때 가장 중요한 성공 조건은, 컬럼 개수와 데이터 타입을 맞춰야한다는 것입니다.

컬럼 개수가 맞지 않으면 에러가 뜰 수 있기 때문에, 반드시 컬럼 개수를 맞춰야 하고 빈 컬럼이 있다면 아무 값을 넣어서라도 채워야만 합니다. 또, 출력되는 페이지여야 의미가 있는데 우리가 보지 못하면 아예 의미가 없어지는 공격 유형이기 때문입니다. 그렇기 때문에 컬럼 안에 있는 페이지가 보이는 페이지인지 확인하는 것이 굉장히 중요하게 됩니다.



그래서 보통 ORDER BY를 통해 컬럼 개수를 찾고, UNION SELECT 1,2,3 등 값을 넣어보여 화면에 어떤 숫자가 뜨는지 확인 후 데이터를 빼오는 작업을 진행합니다.





다음은, Error-based SQL입니다. DB 에러 메시지를 일부러 발생시켜서 그 안에 포함된 정보를 빼내는 공격으로, DB가 에러를 낼때 보여주는 에러 메시지를 이용하는 방식입니다.



DB는 에러가 날때 종종 DB이름이라던가, 테이블 이름, 컬럼 이름, 심지어는 데이터 일부까지도 종종 보여주기 때문에 공격자는 이를 이용해 에러 메시지에 자신이 원하는 정보를 실어서 나오게 합니다.



원래 쿼리가

```
SELECT * FROM users WHERE id='1';
```

이런 식이라면 일부러



```
1' AND 1=CAST((SELECT database()) AS int) --
```



이런 이상한 연산(문자열인 database에 int로 변환을 하려고 하는)을 넣게 되면



에러 메시지로 nvalid input syntax for integer: "my_database" 같은 것들이 뜰 수 있습니다.



여기서 "my_database"가 DB 이름이기 때문에 공격자는 결국 원하던 DB이름을 탈취하는 것을 성공하게 되는 것입니다.



DB종류마다 페이로드가 다른데,

MYSQL는 extractvalue, updatexml. SQLite는 CAST, MSSQL은 convert, Oracle은 utl_http등 다양하다. 페이로드의 자세한 설명과 활용은 이후 실습에서 진행 될 에정입니다!





다음으로 알아볼 것은 Blind SQLi. 결과가 안 보여도, 시스템의 반응을 이용해서 데이터를 추측하는 공격입니다.





데이터 출력도 없고 에러 메시지도 없는 상황에서 눈으로 보지 못하니 추측으로 알아내게 되는 공격인데, 직접 보는 게 아니라 참/거짓 또는 시간 등으로 알아내보는 것입니다.



Blind SQLi는 Boolean-based Blind SQLi, Time-based Blind SQLi 등 종류가 있는데,

그 중 Boolean-based Blind SQLi은 참, 거짓 반응으로 추측하는 방법으로 ' AND 1=1 -- 등으로 반응 확인 후, 데이터를 추측해서



```
' AND (SELECT SUBSTRING(password,1,1)='a') --
```

맞으면 정상 페이지로, 틀리면 다른 페이지로 가게 하며 글자를 찾는 방법 등이 있다. 이렇게 한 글자씩 맞춰 결국 비밀번호를 완성하는 것.





다음으로 Time-based Blind SQLi은 응답 시간으로 판단해

```
' AND IF(1=1, SLEEP(3), 0) --
```

3초 느려지면 트루.



```
' AND IF(SUBSTRING(password,1,1)='a', SLEEP(3), 0) --
```

맞으면 느려지고, 틀리면 바로 응답하게 하는 그런 방식을 사용합니다.

SQL가 보안 관점에서 막히는 것은 서버 코드 설계의 문제이기 때문입니다

코드와 데이터를 분리해서



```
query = "SELECT * FROM users WHERE id=?"
execute(query, [id])
```



이런식으로 그냥 문자열 데이터로 처리되게 하면 되는데, 이렇게 되면 SQL이 먼저 컴파일되고 값이 들어가기 떄문에 입력값이 SQL 문법을 바꿀 수 없게 됩니다.



일반 방식은 문장 중간에 끼어들어 바꿀 수 있다면, Prepared방식은 문장을 다 만들고 빈칸에 값만 채윅 때문에 문장 구조를 밖굴 수 없게 된다. 여기서 ORM이라는 도구가 쓰이기도 하는데 ORM은 SQL을 직접 쓰지 않고, 코드(객체)로 DB를 다루게 해주는 도구입니다,.



DB를 객체처럼 다루게 해주기 때문에 큰 도움이 됩니다.



여기서, 왜 그럼 SQL을 그냥 쓰느냐는 의문이 들 수 있는데, ORM도 결국 내부에서는 SQL를 만들기 때문입니다. 다만, 우리가 직접 SQL을 만들지 않기 때문에 자동 처리가 되어 안전하고 편안하게 쓸 수 있게 된다. 애초에 ORM을 쓰는 것은 SQLI를 피하려고가 아니라 편의성을 위해서이다. SQL은 직접 제어로 강력하고 직관적이기 때문에, 그리고 어차피 문제가 생기면 SQL을 봐야하기 때문에 쓰이는 것입니다, .



다음으로 입력값 필터링이 있는데, 이건 위험한 입력을 걸러내는 것으로 핵심은 아니고 보조수단 정도의 방어 방법입니다.

길이 제한을 걸거나, 문자 제한, 특수문자 차단 등을 걸어두는 방법. 허용된 것만 받는 화이트 리스트 방식도 있습니다.









## C2



C2는 해커가 감염된 컴퓨터를 원격으로 조종하기 위한 통신 채널입니다.

해커가 해킹한 컴퓨터를 원격으로 효율적이게 조종하기 위해 만든 채널이라고 생각하면 됩니다.



실제 서버 공격 흐름과, 통신 방식, 실제 툴을 중심으로 학습을 이어가 뻗어나갔습니다





서버 공격 흐름은,



- 악성코드 감염

- C2 서버 연결

- 명령 수신

- 정보 탈취 or 추가 공격

으로 생각할 수 있습니다.



초기에 피싱 메일, 취약한 웹사이트, USB, SQLI 등을 통해 침투하여 악성 코드를 심고 실행시킵니다.

그 다음 C2 서버와 연결을 하게 되는데, 여기서 매우 중요한 점은 감염된 PC가 먼저 나간다는 것입니다.

다음으로는 해커가 보낸 명령을 C2가 감염된 PC로 전달을 하게 되고, 마지막으로 감염된 PC가 실행 후 결과를 다시 C2로

보냅니다. 시작 프로그램 등록이나 백도어 설치를 통해 지속성을 유지하고, 같은 네트워크를 쓰는 다른 PC에 감염도 시킵니다





C2 서버 안에서는 실제로, 감염된 PC를 등록하고 명령을 저장하는 일을 하게 됩니다.



명령 수신 과정에서 제일 중요한 것은 아까 적었듯 감염된 PC가 먼저 물어본다는 점입니다. 이게 중요한 이유는 방화벽 때문인데,

감염된 PC가 먼저 요청해 명령을 받아 실행하고 결과를 POST로 보내는 형식으로 진행되어 전부 내부 -> 외부 통신으로 처리되게 됩니다,



이때 이 부분을 공부하며 헷갈렸던 점은, POST로 결과 보낼 때 방화벽은 어떻게 되지? 라는 궁금증이었는데,

이것도 그냥 나가는 요청으로 통과가 되게 됩니다.



감염된 PC가 C2에게 GET > reponse(응답)으로 자동으로 들어옴 -> 감염된 PC 실행 -> 감염된 PC가 C2에게 POST/result 요청하기 때문에 방화벽 입장에선 내부 -> 외부 요청으로 생각되어 허용되게 됩니다.



여기서 또 궁금했던 점은, 명령을 수행한 뒤 곧바로 GET으로 새로운 명령을 대기하게 되는가?라는 궁금증이었는데,

바로 GET 하지 않고 주기적으로 하게 된다고 합니다.



이유는



1. 은닉성

2. 트래픽 패턴 위장

3. 서버 부담 줄이기



셋 정도로 생각할 수 있습니다.





감염된 PC를 등록할 때는 IP뿐 아니라 고유 식별자 + 많은 정보를 기반으로 관리하게 되는데, 감염시 고유 ID를 생성해

```
bot_id = a8f3c9d1
```

예시로 이렇게 등록했다면 이걸 기반으로 계속 사용하게 됩니다.







다음으로 C2 서버의 통신 방식에 대해 설명해보자면, HTTP/HTTPS, DNS tunneling, 암호화 통신 등을 씁니다.

이유는 간단히도, 탐지를 피하려는 이유 때문입니다.



그래서, HTTP와 HTTPS 중에서는 대부분 HTTPS를 더욱 선호하게 되는데, HTTPS는 TLS 덕분에 암호화 된 통신이 가능하기 때문입니다. 내용을 숨기기에는 더욱 도움이 되어 탐지에 어려움을 줄 수 있기 때문에 당연히 C2 서버를 운영하는 해커 입장에서는 HTTPS를 더욱 더 선호할 수 밖에 없게 됩니다. 그리고, 요즘 인터넷은 대부분 HTTPS를 쓰기 때문에 정상 트래픽으로의 위장이 쉬워지기도 합니다



여기서 드는 의문은, 그럼 보안 장비는 어떻게 HTTPS의 내용이 안 보이는데도 C2를 탐지하는가. 인데, 핵심은 내용이 아니라 패턴을 확인한다는 잠에 있습니다. 트래픽 패턴을 분석한다던가, 목적지 분석, 트래픽 크기와 형태 분석, TLS 정보 분석(서버 주소, 인증서 정보, 접속 도메인 등)을 통해 비정상 활동을 분석할 수 있습니다. HTTPS는 내용은 숨기지만 행동을 숨길 수가 없기 때문이죠.





그리고 이 패턴 탐지를 피하기 위해 해커들은 주기성을 꺠는 랜덤 딜레이(jitter), 정상 트래픽처럼 위장, 트래픽 섞기, 데이터 크기 랜덤화, DNS/CDN 이용, Beacon 줄이기 등을 활용합니다. 이렇게 정상처럼 보이는 행동들을 잡기 위해서는 정상처럼 보이는 하나보다 여러개를 모아 이상함을 찾고, 단일 PC말고 전체 패턴을 본다던가, 희귀성을 분석하고, 시간 패턴을 분석, 행동 조합 보기, 엔드포인트(PC내부) 분석 등을 통해 잡아낼 수가 있습니다.





다음으로 DNS tunneling이 있는데,

이를 이해하기 위해선 우선 DNS에 대해 알아야 합니다. DNS란 도메인 이름을 IP 주소로 바꿔주는 시스템으로 우리가 쓴 도메인과 컴퓨터가 실제로 알아듣는 IP 형식이 다르기 때문에 변환을 해주어 IP로 접속하게 해주는 시스템입니다.



우리가 google.com로 입력했을 때, DNS가 142.250.206.14로 답해주기 때문에 그 IP로 접속을 할 수 있게 됩니다.



여기서 DNS tunneling이 사용되게 되는데, 이 DNS 요청/응답에 데이터를 몰래 실어서 주고 받는 것입니다.

원래의 DNS는 google.com의 IP가 무엇인가 같은 것을 묻는 용도인데 공격자가 이 DNS를 데이커 운반 통로로 활용하는 방식입니다.

DNS를 쓰는 이유는, 단순하게도 많은 환경에서 항상 허용되고, 웹이 막혀도 DNS 질의는 통과되는 경우가 많은데다 보안 장비가 HTTP/HTTPS보다는 DNS를 조금 더 느슨하게 보는 경우가 있기 때문입니다.





DNS tunneling은 보통 이렇게 흘러갑니다.

- 감염된 PC가 보낼 데이터를 준비함

- 그 데이터를 잘게 쪼갬

- 도메인 이름처럼 보이게 인코딩함

- DNS 질의에 넣어서 보냄

- 공격자가 가진 권한 DNS 서버가 그 질의를 받음

- 질의 안에 숨은 데이터를 꺼냄

- 필요하면 DNS 응답에 명령도 실어서 돌려보냄



원래의 DNS 요청에서는 www.example.com의 (http://www.example.xn--com-yh0o/) 의미가 www.example.com의 (http://www.example.xn--com-yh0o/) IP 알려달라는 뜻과 같다면,

DNS tunneling에서는 공격자가 도메인 앞 부분에 데이터를 숨겨넣어 hello.example.com 이런 식으로 만듭니다.

이러면 질의가 공격자 소유 DNS 서버까지 갔을 때, 공격자는 hello를 보고 감염 pc가 hello라는 데이터를 보낸 것을 확인할 수 있게 됩니다.



하지만, 실제로 그냥 문자열을 이렇게 보내는 경우는 많지 않고 실제로는 파일 조각이나 명령 결과같은 바이너리 데이터가 많기 때문에

인코딩을 먼저 해 Base32, Base64, HEX 등으로 보냅니다. 도메인의 이름에 쓸 수 있는 문자가 제한적이기 때문입니다.



그래서 긴 데이터를 보낼 때는 쪼개서 여러번 보내는데, 구문 느낌으로 보면

<data>.<ssession><domain>

으로 보내게 됩니다.



bcd1234.01.attacker.com

각 부분 의미를 풀면:

- abcd1234 → 실제 숨긴 데이터 조각

- 01 → 세션 번호나 순서 번호

- attacker.com → 공격자가 소유한 도메인

이 됩니다.



조금 더 복잡하게는:

<seq>.<clientid>.<data>.attacker.com



예:

03.host7.abcd1234.attacker.com



의미는 대충:

- 03 → 3번째 조각

- host7 → 감염된 PC 식별자

- abcd1234 → 데이터

- attacker.com → 공격자 DNS 서버

즉, DNS 이름 자체가 작은 패킷처럼 쓰일 수 있게 됩니다.





마지막으로 실제 툴에 대해 알아보면 Metasploit과 Cobalt Strike 등이 있는데, Cobalt Strik가 제일 유명하고 양한 공격 기능으로 인해 가장 많이 악용되는 툴이며, Metasploit 또한 exploit + payload + C2 기능을 가지고 있으며, Meterpreter라는 쉘을 제공합니다.





실습은 문제 받아서 곧바로 라이트업 작성예정입니다!









### RSA



RSA에 대해서 알기 위해선 대칭키와 비대칭키에 대해서 먼저 이해해야 하는데, 대칭키는 키 1개를 가지고 비대칭키는 2개를 가지고 있습니다.



대칭키 암호화란, 하나의 키로 암호화 + 복호화를 같이 하기 때문에 속도가 빠르고 파일 암호화에 사용이 됩니다.

대표적인 알고리즘으로는 AES와 DES가 있는데, 여기서 만들어진 키를 안전하게 전달할 때 비대칭키 암호화 기술이 많이 쓰입니다.





비대칭키 암호화의 핵심은, 키가 2개가 있는 것으로 공개키와 개인키로 나뉘어 공개키로 암호화 후 개인키로 복호화를 하게 됩니다.

키 교환 문제는 해결되지만 느리다는 단점이 있고, 이때 대표적으로 쓰이는 게 우리의 주제인 RSA입니다.



RSA는 큰 수의 소인수분해는 어렵다는 아이디어에서 출발했는데 동작 흐름을 쉽게 설명해보면



- 두 개의 큰 소수 선택 (p, q)

- n = p × q

- 공개키 / 개인키 생성

- 공개키로 암호화

- 개인키로 복호화

이러한 흐름을 가지고 있습니다.



주로 HTTPS, 로그인 인증, 디지털 서명, 키 교환 등에 쓰입니다.





AES에 대해 먼저 조금 더 알아보면, 대칭키 암호화의 대표적인 방식인데 대칭키라는 것 자체가 빠르고 대용량 데이터가 처리가 가능하다는 장점이 있기 때문에 현실에서 굉장히 많이 쓰이게 됩니다. 문제는 아까 말했듯 키가 하나니까 이것이 잘못되면 안되기 때문에 전달 과정에서 RSA가 쓰이게 되는 것입니다.





즉, RSA는 키를 안전하게 전달을 하고, AES가 실제 데이터를 빠르게 암호화하는. 그렇게 협업을 하는 구조가 됩니다.





RSA의 실제 활용 사례로는 특히 웹사이트에서의 활용을 들 수가 있는데 우리가 웹사이트에 들어갈 때 서버가 RSA 공개키를 주고, AES키를 RSA로 암호화해서 보낸 후 AES로 통신을 하게 됩니다.

이유를 HTTPS로 쉽게 이해해보면 인터넷은 다 공개된 길이기 때문에 중간에 누가 훔쳐볼 수 있어서 RSA 공개키로 잠가서 보내게 해준 뒤, 사사용자가 AES키를 만들어 그 키를 RSA로 잠가서 보내 중간에서 봐도 못 읽고, 개인키를 가진 서버만 열 수 있게 만든 것입니다.

RSA는 비밀 열쇠를 안전하게 전달하는 역할로, AES는 실제 대화 내용을 보호하는 역할로 활용이됩니다. 이렇기에 HTTPS는 결과적으로 RSA와 AES를 함께 사용하는 하이브리드 암호 방식이 됩니다.









이 RSA의 동작 과정으로는 키 생성, 암호화, 복호화가 있는데 이 중 키 생성에선 공통적으로 n을 가진 뒤 큰 소수 2개를 고르고(p,q) 둘을 곱해 계산을 통해 e,d를 생성하게 됩니다. n은 공개가 되지만 p,q가 비밀이기 때문에 n만 보고 p,q를 찾기가 어렵게 되는 것입니다.



n = p x q인데 p,q를 모르면 d를 못 구하게 되고, 근데 p와 q를 찾기가 소인수분해로 이루어져 찾기가 힘들기 때문에 보안이 되는 것입니다.



이를 푸는 방법으로는 두가지를 다 알고 있거나, 개인키가 없을 때



- n = p × q

- p, q를 구해야 하기 때문에

- φ(n) 계산

- d 계산

이 과정을 거치기도 합니다. 어려운 이유는, n이 보통 2048비트로 엄청 크기 때문에 소인수분해가 현실적으로 거의 불가능하기 때문인데

CTF 같은 곳에서는 일부러 좀 약하게 내주는 경우가 있어 n이 작거나, p,q 차이가 작아 Fermat 공격( √n 근처에서 차이값을 이용해 빠르게 소인수분해하는 방법)이 가능하거나, d가 작아서 Wiener 공격(e/n을 이용해 연분수로 d를 찾아내는 공격) 등을 이용하게 됩니다.





이러한 RSA를 만들기 위해서는 프로그램을 쓰는데, 사실상 프로그램이 아니라 수학으로 만드는 구조이기 때문에 원래는 수학 공식으로 생성을 합니다. 하지만 실제에서는 프로그램이 자동으로 해주기 때문에 OpenSSL, GnuPG 등의 프로그램을 쓰거나 Python 코드로도 만들 수가 있게 됩니다.



이를 푸는 도구 또한 알아보지 않을 수가 없는데, 원래 RSA가 못 풀게 만든 것이기 때문에 만능 툴은 아니고, 아무 RSA나 풀 수 있는게 아닌 취약한 경우에만 풀게 됩니다. 대표적인 도구들로는 RsaCtfTool, SageMath 등이 있습니다.
